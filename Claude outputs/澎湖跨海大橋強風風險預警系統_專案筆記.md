## 一、專題定位與設計理念

### 1.1 問題背景
澎湖為全台風力最強地區之一，跨海大橋機車通行常受強風影響，是明確可查證的在地安全問題。市面上既有氣象 App（CWA 官方 App、Windy 等）僅提供區域概化的氣象資訊，**無法回答「我現在要不要騎車過跨海大橋」這種特定地點、特定時刻的決策問題**，此為本專題的切入縫隙。

### 1.2 為何不做硬體感測網
- 澎湖高鹽害環境對硬體感測器的長期可靠度是實務挑戰，非資工系專長，且無廠商投入代表市場誘因不足。
- CWA 已有官方測站與開放資料 API，資料品質有保障，不需重複建置。
- 結論：**改走「資料整合 + 決策支援」路線**，完全不需自建硬體。

### 1.3 核心設計理念
1. **問題導向**：所有技術決策服務於「跨海大橋強風機車事故風險」這個具體問題，不為技術而技術。
2. **資料源可信、免維運**：完全依賴政府開放資料（CWA），不需人工審核內容，保證系統永續性。
3. **模型可解釋、漸進迭代**：第一版採規則式風險等級（非黑盒模型），以公路局官方管制標準為依據，之後有歷史資料可再升級為統計/機器學習模型。
4. **使用者情境優先**：介面設計聚焦單一具體情境（今天能不能安全騎車過橋），而非功能堆疊。

### 1.4 曾評估但捨棄的方向
- **UGC 評分留言（如店家評論）**：因冷啟動困難（Google/FB 已佔據使用者習慣）、具名批評的名譽權/法律風險、審核人力成本，且技術深度不足以支撐專題份量，故捨棄。
- 保留「多元內容」精神的替代做法：改用**開放資料整合**（停水停電公告、活動資訊等）與**匿名聚合式群眾回報**（如「今日大橋風況回報」），避免評論類產品的核心風險。

### 1.5 跨系所合作（加分項，非依賴項）
決定**先把資工系能獨立完成的部分做扎實**，跨系合作留作日後加分，不影響主線進度。潛在合作對象（依澎科大系所）：
- 海洋遊憩系（海況/活動安全準則）
- 餐旅管理系（在地飲食內容）
- 應用外語系（多語系介面）
- 電機/電信工程系（若未來擴充硬體）

### 1.6 專題方向改版（2026/10/6 決定）
**背景**：資料蒐集與規則式風險判斷都已完成並驗證可行（見第五節），但重新檢視後，認為「查表式」的風險判斷（風速超過門檻 → 回傳對應標籤）技術深度不足，沒有運算或推論的成分，不足以撐起資工系專題的份量。此改版由學生主導決定，**不受指導教授既定題目限制**（題目可自由更換），記錄於此供日後說明決策脈絡。

**新的核心敘事**：
> 在測站資料存在系統性缺值與斷檔的真實限制下，研究如何用機器學習方法做短期強風風險預測，並比較不同缺失值插補策略對預測效果的影響，以澎湖跨海大橋（西嶼站）為案例驗證。

**維持不變**：問題背景、資料源（CWA 開放資料）、澎湖跨海大橋案例場景、公路局官方管制標準（改為「現行規則式方法」，作為新模型的 baseline 對照組，而非最終產出）、已完成的資料蒐集 pipeline 與歷史資料分析。

**新增三個主要模組**：
1. **缺失值插補模組**：第 5.7、5.8 節發現的陣風缺值、西嶼站長期斷檔問題，正式升格為研究子題，而非順手解決的工程雜事。比較前向填補、線性內插、氣候平均（月×時）、測站迴歸等方法，並設計「遮罩評估」實驗（人工挖空已知區段、比較還原誤差）。初步雛形結果見 5.9。
2. **短期風險預測模組**：預測目標為未來 1～3 小時的風速／風險等級是否升級，而非只讀取當下。先用 baseline（persistence、線性外插、氣候平均）建立比較基準，再嘗試機器學習方法（梯度提升樹為優先，之後可選嘗試 LSTM）。評估方式延用遮罩評估/預測評估的召回率、精確率框架。
3. **系統工程與案例驗證模組**：現有即時資料收集 pipeline、`risk_assessment.py` 規則判斷（保留作為現行官方標準 baseline）、前端儀表板（可選，第二年視進度再做）。

**兩年時程規畫（參考，依實際進度調整）**：
- Year 1 上半：插補模組文獻回顧＋正式實作＋評估（修正 5.9 雛形實驗的資料洩漏問題，切訓練/測試期）；同時持續累積即時資料。
- Year 1 下半：預測模型 baseline 與第一版機器學習模型，於西嶼站驗證。
- Year 2 上半：模型優化、不確定性量化、泛化到其他測站測試、系統整合（預測結果接回儀表板）。
- Year 2 下半：論文寫作、答辯準備、（可選）跨系所合作加分項。

### 1.7 文獻引用與主題重複的疑慮（討論記錄，2026/10/6）
學生提出疑慮：多引用文獻會不會讓專題跟別人的研究撞題？討論結論：
- 多引用文獻是用來**定位**專題（說明前人做了什麼、自己哪裡不同），不是造成重複的原因；完全不引用、讓人看不出跟既有研究的關係，反而更容易被認為是重複。
- 「重複」分兩層：文字層面（抄襲，用自己的話轉述＋正確引用即可避免）與主題層面（別校也可能做類似主題，這是常態，教授真正在意的是「差異說明」寫得夠不夠清楚）。
- 本專題有幾個別人不容易複製的具體組合：澎湖跨海大橋場域、CWA 開放資料整合、公路局官方管制標準作為風險門檻（非自訂）、1.6 節的插補與預測研究設計。

## 三、理論基礎與文獻依據

依教授建議，專題需明確回答「理論依據是什麼」「與既有研究的差異在哪」，目前掌握的三層依據：

| 層次 | 內容 | 角色 |
|---|---|---|
| 相關研究 | 〈利用氣象物聯網與人工智慧判讀技術設計無人機河川災害預警系統〉（NDLTD 碩士論文） | 證明「氣象 IoT + AI/規則判讀」架構在防災領域已有先例，本專題為同一方法論在「離島橋梁強風」場域的垂直應用 |
| 工程理論基礎 | 〈斜張橋之抗風設計與風洞試驗〉 | 說明風速影響橋梁/車輛安全有嚴謹風工程理論支撐，非憑空假設 |
| **法規依據（風險門檻直接來源）** | **公路局澎湖跨海大橋風力管制標準** | 風險判斷邏輯的權威來源，非自訂門檻 |

### 3.1 公路局官方管制標準（風險模型核心依據）

| 階段 | 平均風速門檻 | 管制措施 |
|---|---|---|
| 加嚴門檻（研擬中） | 7 級風（約 13.9 m/s 以上） | 機車/人行/自行車道擬加嚴門檻 |
| 第一階段管制 | 8 級風（約 17.2 m/s 以上） | 封閉機車專用道、人行道、自行車道；快車道降速至 40 或 30 km/h |
| 第二階段管制（全封） | 10 級風（約 24.5 m/s 以上） | 全橋預警性封閉，禁止所有車輛通行 |
| 解除管制 | 風力減弱至安全標準以下 | 經公路局派員完成全橋巡檢確認結構安全後恢復通車 |

**關鍵發現**：官方標準採用「平均風速」而非「陣風（最大瞬間風速）」作為判斷基準，這直接解決了系統設計上的陣風缺值問題（詳見第五節）。

### 3.2 待補充的文獻方向
- 早期預警系統（Early Warning System）設計理論
- 缺失值插補（Missing Data Imputation）理論，可呼應本專題實際遇到的資料缺值問題

## 四、資料來源：CWA 開放資料平台

- **資料集**：`O-A0001-001`（現在天氣觀測報告）
- **申請方式**：opendata.cwa.gov.tw 註冊會員 → 取得 Authorization 授權碼
- **澎湖縣測站**（共 9 站）：七美、望安、湖西、西嶼、花嶼、東吉島、澎湖（馬公）、吉貝、畜試所澎湖
- **關鍵欄位**：`WindSpeed`（風速）、`WindDirection`（風向）、`GustInfo.PeakGustSpeed`（陣風）
- **缺值代碼**：`-99` 等，需程式主動過濾，不可直接代入計算
- **實測更新頻率**：**每小時一筆**。資料庫中所有 `obs_time` 皆落在整點（分鐘為 00）。新資料約在整點後 10～35 分鐘才出現在 API，時間不固定。
  - *更正*：本筆記先前版本寫「約每 30 分鐘更新」，那是把排程間隔（30 分鐘）與資料更新頻率混為一談；2026/9/19 查驗資料庫後確認為每小時。
  - 排程改為每 10 分鐘輪詢一次，目的是縮短資料延遲（原 30 分鐘輪詢，延遲最長約 30 分鐘）；重複抓到的資料由 UNIQUE INDEX 自動略過，不會污染資料庫。

### 4.1 JSON 結構的兩種格式（已處理相容）
- 手動下載檔案：`raw_json["cwaopendata"]["dataset"]["Station"]`
- 直接呼叫 REST API：`raw_json["records"]["Station"]`

## 五、關鍵技術問題與解決記錄

### 5.1 SSL 憑證驗證失敗
**現象**：`CERTIFICATE_VERIFY_FAILED`、`Missing Subject Key Identifier`
**原因**：部分台灣政府網站憑證缺少完整 Subject/Authority Key Identifier 擴充欄位；Python 3.13 起 SSL 模組預設啟用更嚴格檢查（`VERIFY_X509_STRICT`），導致原本合法網站被誤判。
**解法**：僅關閉 `VERIFY_X509_STRICT` 這一項過嚴檢查，其餘憑證驗證（過期、CA 信任、主機名稱）正常運作，比整個 `verify=False` 安全。

### 5.2 陣風資料大量缺值
**現象**：9 個測站中，多數站陣風缺值率 30%～100%（望安 90%、東吉島/湖西 100%）。
**因應**：確認官方管制標準以「平均風速」為主要依據後，陣風降級為輔助/加權參考欄位，不影響核心風險判斷邏輯。

### 5.3 吉貝站持續缺值（風速/陣風皆 100%）
**原因查證**：吉貝遊客中心與石滬文化館自 113/11/4 起進行整修工程，導致斷電斷網，吉貝合作氣象站同步停止觀測。原定 114/9 完工，**惟截至 115/9（目前）仍未完工，工程持續延宕中**。
**論文角度的價值**：此案例修正了「鹽害導致設備故障」的原始猜測，改以官方查證結果為準，並帶出「環境感測系統可靠度不只取決於設備本身，也高度依賴周邊基礎設施穩定性」的系統設計洞察，可寫入限制/未來工作章節。

### 5.4 新舊資料庫欄位升級與銜接
**現象**：`fetch_weather.py` 加入風險等級計算後，舊資料庫沒有 `risk_level`/`risk_label` 欄位。
**解法**：`init_db()` 用 `ALTER TABLE ADD COLUMN`（包在 try/except 裡）安全升級，不清空舊資料。
**追加問題**：若新程式抓到的 `obs_time` 與資料庫中舊紀錄重複，因防重複機制（UNIQUE INDEX）會直接跳過寫入，導致舊資料的風險欄位永遠無法透過「重新抓取」補上。
**解法**：另寫 `backfill_risk.py` 一次性回填工具，直接用資料庫裡既有的 `wind_speed` 回頭計算並 `UPDATE` 風險等級，不需重新呼叫 API。

### 5.5 排程中斷造成資料斷檔（2026/9/18）
**現象**：資料庫中 9/18 05:00 到 12:00 之間缺了 6 個整點觀測（約 54 筆），涵蓋率 88%（50 個預期時點、實得 44 個）。對應的排程空窗為 05:11 到 12:35，約 7.4 小時，推測為電腦夜間休眠。
**限制**：CWA 這支 API 只回傳「最新一筆」，斷檔期間的資料無法從它補回。若要補，需改用 CODiS（氣象觀測資料查詢系統）的歷史逐時資料下載。
**因應**：
- `scheduler.py` 於執行期間要求 Windows 不因閒置休眠（無法防止闔蓋或手動睡眠，需另外調整電源選項）。
- 排程啟動時檢查資料庫最後一筆觀測距今多久；執行中若兩輪間隔超過設定值 2 倍，印出休眠警告。
- `stats.py` 新增斷檔偵測，列出每段斷檔與缺少的時點數。
**論文角度的價值**：可寫入「資料品質與限制」，並說明系統設計上為何需要斷檔偵測與歷史資料補齊機制。

### 5.6 測站之間風速差異大，須指定橋區參考站
**現象**（2026/9/17～19，約兩天資料）：各站平均風速：西嶼 7.4、澎湖（馬公）3.9、畜試所澎湖 3.2 m/s；西嶼約為澎湖站的 2 倍。
**影響**：原 `stats.py` 把全測站合併統計風險等級分布，會被遠離橋區的測站稀釋而失真。
**因應**：`stats.py` 改為逐站統計，並以**西嶼站**作為橋區參考站（就目前所知，西嶼為離跨海大橋最近的測站）。
**限制**：測站風速仍不等於橋面實際風速，橋面受地形與橋體影響可能與測站有落差，屬於需在論文限制章節說明的項目。

### 5.7 陣風缺值是否為非隨機缺值（待驗證）
**初步觀察**：各站有紀錄的陣風最小值都落在約 8～11 m/s；澎湖、西嶼、畜試所、花嶼在缺陣風的時段，平均風速較低，看似陣風只在超過某門檻時才有紀錄。
**反例**：七美、湖西的趨勢相反（缺陣風時平均風速反而較高），且湖西、望安有陣風的筆數僅 1～2 筆，樣本太少。
**目前結論**：**證據不一致，不能下結論**。需要更長時間的資料，或對照 CODiS 歷史資料再判斷。若日後確認為非隨機缺值，則用平均值等簡單方法插補會產生偏誤，可作為缺失值插補文獻回顧的實例。

### 5.8 歷史資料分析結果（西嶼站，2016-06-30～2026-09-18，分析於 2026/9/19）
**時間對齊**：與即時 API 重疊的 44 筆風速逐筆比對，歷史資料時間平移 0 小時時 44 筆全部相同，兩份資料的時間定義一致。
**風級頻率**（有效風速 77,161 小時）：平均風速 ≥7級 7,162 小時（9.3%）、≥8級 1,175 小時（1.5%）、≥10級 36 小時（0.05%）。資料較完整的 2022～2025 年，每年 ≥8級約 150～220 小時、≥7級約 800～1,170 小時。10 級只出現在 2016、2023、2024 三年，皆落在颱風期間。
**季節性**：10 月至隔年 2 月為主，12 月最高（≥7級占 27.6%、≥8級占 5.3%）；7～9 月偶有颱風造成的事件。
**強風事件**：逐小時連續達 8 級的時段共 438 段，其中 59% 只持續 1 小時。間隔 6 小時內合併後為 193 個事件（每年約 12～31 個，中位跨度 3 小時，≥24 小時者 24 個）。**設計意涵**：逐小時判斷燈號會頻繁閃爍，需要平滑或遲滯機制，並以「事件」為單位呈現。
**來源資料缺口**（原始 CSV 本身即為缺值代碼，非匯入錯誤）：西嶼風速缺 12,407 小時（13.9%）。連續缺 7 天以上共 9 段，最長為 2019-03-01 起 111 天、2021-02-08 起 64 天、2018-11-23 起 28 天。其中 2021 年 1～2 月與 2018 年 11～12 月位於強風季，使該季頻率被低估。2022 年後基本完整。
**陣風品質**：有 44 筆陣風小於平均風速（全部在 2017～2018 年，例如 2017-07-30 平均 12.1、陣風 3.5），屬異常值，應於匯入時標為缺值。
**陣風係數**：中位數 1.57；平均風速 ≥7 級時中位數 1.52（第 10～90 百分位 1.40～1.71）。平均風速未達 8 級、但陣風已達 8 級風速的時數，占有陣風紀錄時數的 21.8%。
**測站比較與補值**：西嶼風速約為澎湖（馬公）的 2 倍（迴歸斜率 1.84），西嶼達 8 級的 1,175 小時中，澎湖同時達 8 級僅 2 小時。以澎湖線性換算補西嶼（訓練 2022～2024、測試 2025～2026）整體 R² = 0.82、RMSE = 1.9 m/s，但對 8 級事件的召回率僅 22%、對 7 級僅 49%。**結論**：澎湖站不適合在西嶼缺值時當補值來源。這只是簡單線性基準，尚未測試其他測站與較複雜的方法，不是最終結論。

### 5.9 插補方法比較：遮罩評估雛形實驗（2026/10/6，支撐 1.6 節改版方向）
**目的**：驗證「插補方法選擇」是否真的是值得研究的問題，而不是順手處理的小事，作為專題改版的第一個雛形證據。
**做法**：`impute_experiment.py`。用西嶼站 2022～2025 風速較完整的時段，在已知真值的時間點人工挖空不同長度的區段（1～168 小時，模擬真實斷檔長度分布），比較 5 種方法還原的誤差：延用前值、線性內插、月×時氣候平均、澎湖站迴歸、以及自訂的 hybrid（≤24 小時用內插、超過用迴歸）。400 次有效試驗。
**已知簡化（下一步要修正才能當正式方法）**：climatology 與 regression 用全部歷史資料配適，包含評估點本身，有資料洩漏；挖空起點隨機選取，不是重現資料庫裡實際發生過的斷檔位置／季節；只看風速是否同時達標，沒看事件起訖時間的誤差。

**結果**（平均絕對誤差 MAE，7 級風門檻 13.9 m/s 召回率）：

| 方法 | 短 1-6h MAE／召回率 | 中 7-24h MAE／召回率 | 長 25-168h MAE／召回率 |
|---|---|---|---|
| 延用前值 | 1.33 / 60% | 1.82 / 66% | 3.14 / 35% |
| 線性內插 | 0.91 / 62% | 1.35 / 70% | 2.39 / 49% |
| 月×時氣候平均 | 3.13 / 0% | 2.85 / 0% | 3.02 / 0% |
| 澎湖站迴歸 | 1.54 / 42% | 1.58 / 35% | 1.54 / 41% |
| hybrid（≤24h內插/>24h迴歸） | 0.94 / 62% | 1.35 / 70% | 1.54 / 41% |

**發現**：
1. **氣候平均法召回率是 0%**：用月×時平均去填補，絕對無法還原任何一次達標事件，即使整體 MAE（2.85～3.13）看起來不算誇張。這證明「用平均值補缺」對風險預警系統是結構性不適用的方法，不只是精度不夠而已，是個很好的反例可以寫進方法論章節。
2. **MAE 最低不代表召回率最高**：長時段（25～168h）迴歸的 MAE（1.54）比線性內插（2.39）低，但召回率（41%）反而輸給內插（49%）。代表評估插補方法不能只看誤差大小，必須同時看對「極端事件」的還原能力，這兩個指標會給出不同的最佳方法。
3. **目前設計的 hybrid 規則沒有達到預期效果**：原本假設內插只適合短時段，超過 24 小時該切換成迴歸，但實測線性內插在長時段的召回率（49%）反而比迴歸（41%）好，代表這個切換門檻設錯了，或是需要更好的長時段方法（這正是模組 1 要繼續研究的方向）。
**意義**：這組初步結果已經證明插補方法的選擇會顯著影響「是否能偵測到真正的強風事件」，且簡單直覺的作法（平均值、單一門檻切換）都有明顯破綻，支撐 1.6 節把這個題目正式納入專題核心，而不是順手解決的工程問題。

### 5.10 排程斷檔原因查明，改用 GitHub Actions 收集資料（2026/10/6）
**原因查明**：9/24～9/25 的 41 小時斷檔，是因為使用者當時出國、電腦關機／終端機視窗被關閉，不是單純的閒置睡眠。5.5 節加的防休眠機制（`SetThreadExecutionState`）只能擋住「電腦因為沒人用而自動睡眠」，擋不住使用者主動關機或把筆電帶出門——只要排程綁在本機，使用者不在電腦前就一定會斷。這是方法本身的限制，不是設定沒調好。

**解法**：把即時資料收集移到 GitHub Actions（GitHub 提供的雲端排程執行環境），完全不依賴使用者的電腦。這不是新發明的做法，目前使用的歷史資料來源（Raingel/historical_weather）本身就是用同樣的方式每天自動更新。

**新增檔案**：
- `gha_fetch.py`：重用 `fetch_weather.py` 的 API 呼叫與解析邏輯，把抓到的資料附加到 `gha_log/weather_log.csv`（用 CSV 而非直接寫 SQLite，因為二進位資料庫檔案不適合用 git 頻繁提交）。
- `.github/workflows/collect.yml`：排程設定，每 15 分鐘在 GitHub 的雲端伺服器上執行一次。
- `merge_gha_log.py`：把 `gha_log/weather_log.csv` 併入本機的 `penghu_weather.db`，可以指向本機檔案，也可以直接指向 GitHub 上的 raw 檔案網址抓最新版本再併入；重複的 (station_id, obs_time) 會被資料庫的 UNIQUE INDEX 自動跳過，跟本機 `scheduler.py` 同時跑也不會互相干擾或算重複。
三支都已用模擬資料測過，邏輯正確（風險等級計算、重複跳過都正常）。

**使用者需要自行完成的設定**（這個對話的 GitHub 權限只能操作已連接的 repository，無法代為建立新的）：
1. 在 GitHub 建立一個新的 public repository。
2. 把 `NPU-Wally` 資料夾 push 上去（`.gitignore` 已經擋掉 `api_key.txt` 和 `*.db`，不會洩漏金鑰或上傳大型二進位檔）。
3. 到 repo 的 Settings → Secrets and variables → Actions，新增 secret：名稱 `CWA_API_KEY`，值是 CWA 授權碼。
4. 到 Settings → Actions → General，把 Workflow permissions 設為「Read and write permissions」，否則 workflow 無法把資料 commit 回 repo。
5. push 完後到 Actions 頁籤確認排程開始執行，也可以手動按 "Run workflow" 立即測試一次。

**下一步**：GitHub Actions 穩定運作一段時間後，本機 `scheduler.py` 可以降級為備援，不再是唯一資料來源；之後也可以直接請 Claude 在對話中用 `merge_gha_log.py --url ...` 從 repo 的 raw 檔案把最新資料併入分析，不需要使用者的電腦在線。

## 六、目前程式模組總覽

| 檔案 | 功能 |
|---|---|
| `fetch_weather.py` | 呼叫 CWA API、篩選澎湖 9 站、過濾缺值、計算風險等級、寫入 SQLite（含防重複、SSL 修正、雙 JSON 格式相容）。授權碼改由環境變數 `CWA_API_KEY` 或 `api_key.txt` 讀取；資料庫路徑固定在程式所在資料夾 |
| `scheduler.py` | 每 10 分鐘輪詢並呼叫 `fetch_weather.py`，錯誤自動略過不中斷；執行期間防止 Windows 閒置休眠；啟動時檢查資料庫最後觀測時間，並在偵測到休眠斷檔時警示 |
| `risk_assessment.py` | 依公路局官方風力管制標準，將平均風速換算為四級風險（正常/加嚴/第一階段/第二階段），含缺值的 `UNKNOWN` 狀態處理 |
| `stats.py` | 讀取資料庫，統計時間範圍與資料新鮮度、斷檔偵測、各測站缺值率與風速摘要、逐站風險等級分布、西嶼參考站近況、陣風缺值檢查 |
| `import_history.py` | 從 Raingel/historical_weather（CODiS 整理版）下載西嶼、澎湖等站的逐年逐時 CSV，清理缺值代碼後存入獨立資料庫 `penghu_history.db`（另記錄每個檔案的 sha256 供重現）。西嶼資料自 2016-06-30 起 |
| `impute_experiment.py` | 缺失值插補方法的遮罩評估雛形實驗（1.6 節新方向第一個子題）：人工挖空西嶼站已知風速區段，比較前值延用、線性內插、氣候平均、測站迴歸、hybrid 五種方法的誤差與 7 級門檻召回率；輸出 CSV 至 `analysis_output/插補方法比較_西嶼.csv` |
| `gha_fetch.py` | 在 GitHub Actions 的雲端環境執行，重用 `fetch_weather.py` 邏輯抓取資料，附加到 `gha_log/weather_log.csv`（5.10） |
| `merge_gha_log.py` | 把 `gha_log/weather_log.csv`（本機或 GitHub raw 網址）併入 `penghu_weather.db`，重複資料自動跳過（5.10） |
| `.github/workflows/collect.yml` | GitHub Actions 排程設定，每 15 分鐘自動執行 `gha_fetch.py` 並 commit 回 repo（5.10） |
| `analyze_history.py` | 歷史資料分析：資料品質、7/8/10 級風頻率（逐年、逐月）、強風事件清單、測站比較（用他站代替西嶼會漏掉多少 8 級時數）、陣風係數、與即時資料庫的時間對齊檢查；輸出 CSV 至 `analysis_output/` |
| `verify_db.py` | 驗證資料庫結構是否正確升級、新舊資料銜接是否正常、吉貝站狀態是否與已知事實一致 |
| `backfill_risk.py` | 一次性回填工具，補上舊資料缺少的風險等級（僅需執行一次） |
